# Reorder's optimistic save generalizes fulfillment's race-safe pattern instead of reimplementing it

`AdminProducts.tsx`'s reorder optimistically reshuffled the table before its PATCH resolved, and never reverted on failure — worse, the failure routed through the same `actionError` state used for page-load failures, blanking the whole table instead of just the row order. `src/orders/fulfillmentSave.ts` already solved this exact shape for order fulfillment: a reducer (draft/persisted/saving/error, `saveFailure` reverts draft to persisted) plus a sequence-guarded saver-factory (stale in-flight responses can't clobber a newer confirmed save). Generalized into `src/hooks/useOptimisticSave.ts`; both fulfillment save and reorder now share it. Grilled with Adrian, 2026-09-10 (issue #160, part of map #159).

Decisions and why:

- **Single hook, not a low-level kit.** The original `fulfillmentSave.ts` exposed a reducer + a saver-factory that `FulfillmentControls.tsx` wired by hand (`useReducer` + `useMemo`). `useOptimisticSave<T>(persisted, patch, errorMessage)` hides that wiring, returning `{ draft, saving, error, edit, save }` — the boilerplate that would otherwise be copy-pasted again at the reorder call site is gone instead of duplicated.
- **`fulfillmentSave.ts` survives as a ~5-line specialization; reorder gets no equivalent wrapper.** `useFulfillmentSave(persisted, patch)` calls `useOptimisticSave(persisted, patch, FULFILLMENT_SAVE_ERROR)`, keeping `FulfillmentControls.tsx`'s import and the Polish error string next to the `FulfillmentDraft` type it describes. Reorder is the hook's only other consumer — a wrapper file there would be pure ceremony, so `AdminProducts.tsx` calls `useOptimisticSave` directly.
- **Delete stays untouched.** It isn't optimistic today — `handleDelete` already waits for the DELETE call to confirm before updating local state, so there's no bug to fix. Folding it into `useOptimisticSave` anyway would stretch the hook to a third, differently-shaped mode (direct-commit, no save lifecycle) it doesn't otherwise need. `AdminProducts.tsx` keeps two coexisting pieces of list state instead of unifying them: `ProductsTable` (the reorder hook's consumer) is keyed on `products.length`, so a confirmed delete — the only mutation that changes list length — remounts it with the fresh list, resetting the hook cleanly without either mechanism needing to know about the other.
- **No new test for either thin wrapper, or for reorder's use of the hook.** `fulfillmentSave.test.ts`'s six scenarios (opaque draft shape already, never inspecting `status`/`tracking`) generalized directly into `useOptimisticSave.test.ts` and replace it — per "replace, don't layer," a thin wrapper with no logic past the interface doesn't earn a redundant test. The swap computation reorder needed (`swapProductOrder`, index/direction → new array with `sortOrder` and position both swapped) is real untested domain logic the generic hook can't know about, and got its own direct test.
- **Buttons disable while saving.** Matches the existing `FulfillmentControls` select precedent (disable where pausing costs nothing; the tracking input, where blocking typing would be annoying, stays enabled during its own saves) — extended here to the up/down buttons, which now also avoid firing overlapping PATCHes for what's a one-swap-at-a-time operation.

Consequence: the next admin screen that needs revert-on-failure, race-safe saves reuses `useOptimisticSave` directly — no third reimplementation.
