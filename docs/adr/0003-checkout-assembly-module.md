# Checkout assembly is a frontend module with a pure core

`Cart.tsx` (415 lines, untested) held two drift-prone validity notions — `canCheckout()` gated the button on non-empty fields while `handleCheckout` re-checked with stricter regexes — plus the spread merge (`{ ...paczkomatPoint, ...address }`) that becomes the Order's `shippingAddress` JSON, a cross-boundary contract consumed by order intake and the emails module. Grilled to a design in #48; extraction is #49.

Decisions and why:

- **Pure core + thin hook over a fat `useCheckout()` or a bare function library.** The parts worth testing — validity rules, the shipping-address build, totals — are pure logic; putting them in a hook means `renderHook` mocking forever, while leaving state wiring in Cart keeps the god-file. The module `src/checkout/` owns pure functions with direct vitest coverage; `useCheckout()` is ~thin glue holding state and calling `apiFetch`; `Cart.tsx` is presentation.
- **One validity function, two derived views.** `validateCheckoutDraft(draft)` returns completeness (`missing`) and format (`fieldErrors`) from a single evaluation. The button derives from completeness, the submit guard from format — the existing two-stage UX (button enables when filled in, regex errors surface on submit) is deliberate and preserved, but drift is now structurally impossible: there is no second implementation. Shipping method and paczkomat point are draft validity and live inside; regulamin acceptance and demo mode are UI gating and stay in the component layer.
- **The wire shape stays flat.** `ShippingAddress` is the seven contact/address fields always present, plus `code`/`name` iff `shippingMethod === "paczkomat"` — discriminated by the Order's sibling `shippingMethod`, never by its own shape. A discriminated union on the wire was rejected: every persisted `Order.shippingAddress` row is already flat, the emails module renders that shape, and the payload transits Stripe session metadata where values cap at 500 characters. `buildShippingAddress()` constructs the object explicitly — the paczkomat point's redundant `city` is deliberately dropped instead of surviving or dying by spread order.
- **Noun in `@sznyt/shared`, verbs in the frontend.** The `ShippingAddress` and `ShippingMethod` types join the shared vocabulary (#47) — both sides of the trust boundary speak them, and they replace the backend's `Record<string, string | undefined>` string bag. The functions (`validateCheckoutDraft`, `buildShippingAddress`) stay frontend-only: the backend parses and renders this shape, it never builds or validates it.
- **Module directory, mirroring `backend/orders/` (ADR-0001).** `src/checkout/` holds the draft types, pure functions, hook, `PaczkomatPicker`, and co-located tests. Feature modules for domain logic, layer folders (`hooks/`, `lib/`, `components/`) for generic plumbing. `useCart` stays in `hooks/` — cart state is not checkout assembly.
- **`PaczkomatPicker` quarantines the browser.** easyPack init, the modal callback, and the 375 px viewport sizing workaround live in one component that emits `onSelect(point)`. The hook never touches `window`, so the validate → build → submit paths test without widget mocks, and a widget swap is a one-file change.
- **`checkout-validation.ts` dies into the module; `shipping.ts` is #47's corpse.** The regexes become the format half of `validateCheckoutDraft`. Pricing display (`SHIPPING_COSTS`, threshold, calc) is consolidated by the shared-vocabulary work — #49 only re-points imports.

Consequence: #49 is blocked by #47 so the module is born speaking the shared vocabulary instead of being retrofitted. The contract is documented as "Shipping address contract" in CONTEXT.md's glossary.
