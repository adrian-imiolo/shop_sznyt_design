# A successful add is state the cart owns, not a value `addItem` returns

`CartProvider.addItem` answered "did this add succeed?" with `addToCart(items, newItem) !== items`, computed against the render closure while the state update it had just scheduled ran against `prev`. Both callers used that boolean to decide whether to show the add-to-cart toast. The signal is now a `lastAdd` counter folded into the cart's state, `addItem` returns `void`, and one `CartFeedback` component listens. Grilled with Adrian, 2026-09-11 (issue #167, part of map #159, absorbing candidate #5).

Decisions and why:

- **The signal moved into state because the closure could not tell the truth.** Two clicks landing in one render — the case #70's stock guard exists for — both read the same stale `items`. The scheduled update correctly no-ops the second one, but the returned boolean still reported success. Computing it inside the updater was the obvious fix and is wrong here: `main.tsx` mounts under `StrictMode`, which double-invokes updaters, so assigning to anything outside the updater runs twice in dev. Keeping the counter *in* the state keeps the updater pure, so the double-invoke recomputes the same value from the same `prev` and is harmless. `addItemToState` is that updater, exported pure and unit-tested.

- **Be precise about what the wrong boolean did, because the ticket first overstated it.** A lie requires `prev` to be ahead of the closure, which only happens when an earlier click in the same render already added something — and that click showed a legitimate toast. So the spurious `setAdded(true)` always landed on a toast that was already up: no user ever saw a distinct false "Dodano do koszyka!". What it actually cost was a wrong return value, a second redundant `addToCart` call per add, and an extra stacked timer feeding the bug below. The architectural cost is the one that forced the change: a boolean returned to a caller cannot reach a sibling component, so a single app-level toast is not expressible on top of it.

- **`lastAdd` is a bare counter, not `{ id, at }`.** Only changes carry meaning; the value never renders. The toast says "Dodano do koszyka!" with no product name, so an id would be speculative interface for a message that does not exist. Naming it for the event rather than the count leaves room to carry more later without renaming.

- **One toast for the app, mounted in `ShopLayout`.** `Home` renders one `ProductSection` per product, and each had rendered its own `fixed bottom-8 left-1/2` node — N identical nodes at identical coordinates, compositing whenever two fired inside one window. `ShopLayout` already hosts exactly this category of chrome (`DemoBanner`, `ScrollToTop`, `Footer`) and covers every route that can add to cart. Mounting inside `CartProvider` was considered — it is deeper, since no layout would need to know a toast exists — and rejected as surprising: a context provider that renders DOM mixes state ownership with presentation, and would put the node on admin routes that never call `addItem`.

- **A consequence worth stating: the toast now survives navigation.** It used to die mid-timer whenever `ProductSection` unmounted. That was an accident of where the node lived, not a decision. A persistent mount lets the confirmation finish its window across a route change, which is what the message is actually about — the cart, not the page.

- **No companion hook.** The brief proposed `useAddedToCart` because the lifecycle had two consumers. The app-level mount collapses that to one, which is precisely the condition under which #162 rejected a companion hook for `ProductForm`. What the lifecycle needed was not a hook but a seam a test could reach: `showBriefly(show, ms) => cleanup` is the effect body extracted React-free, so `useEffect(() => showBriefly(setVisible, MS), [lastAdd])` lets React cancel the pending hide before re-running. The stacking bug is fixed structurally by that cleanup; `showBriefly` exists so the fix has a regression test in the node-env suite rather than only an argument.

- **The timer test was proven non-vacuous before being trusted.** `showBriefly` was first written with the shipped behaviour — `setTimeout` and a no-op cleanup — and the regression test failed on the exact assertion it was written for, with the stale timer firing `show(false)` at t=3000 of a window restarted at t=2000. Only then was `clearTimeout` added.

- **Verified by driving a real browser, because at-rest screenshots cannot see this change.** The toast is `opacity-0` when idle, so a `main`-vs-branch diff would pass identically against a completely broken toast. Both halves were run: the two affected routes screenshot byte-identical at 1522×672 (the node moved out of the pages without any visual change), and a driven Playwright script scored 6/6 on the branch against 4/6 on `main`, failing there on exactly the two predicted defects — two toast nodes for two product cards, and the toast gone at t=3.2s of a window restarted at t=2.0s. The `#70` same-tick guard was re-checked on both and holds. chrome-devtools MCP has now failed to connect for four sessions; Playwright remains the standing substitute.

Consequence: the cart owns the answer to "did that add land?", the toast that reports it exists once, and the two pages that used to carry copies of both now just say `addItem(...)`.
